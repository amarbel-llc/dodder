# Box Format RFC Preparation

Status: prep for RFC session
Date: 2026-03-15

## Purpose

Capture all specification knowledge about the box format gathered during the MCP
progressive disclosure work. The code and bats tests ARE the current spec — this
document prepares for formalizing it as an RFC.

## Box Format Grammar

### Structure

Each line represents one object:

```
[<fields>...] <description>
```

- Fields are enclosed in `[` `]` brackets
- Description appears as a trailer after the closing bracket (outside brackets)
- Empty descriptions have no trailer (line ends with `]`)

### Field Order Inside Brackets

1. **Object ID** — first field, no prefix for tags, `!` prefix for types,
   two-part `left/right` for zettels (e.g. `thallium/golem`, `!md`, `konfig`)
2. **Blob digest** — prefixed with `@` (e.g. `@blake2b256-9ft3...`). Omitted
   when empty.
3. **Type** — prefixed with `!` (e.g. `!task`, `!toml-type-v1`). Omitted when
   empty (tag objects typically have no type).
4. **Tags** — bare identifiers, sorted alphabetically

### Tag `%` Prefix Rules

The `%` prefix is strictly an **output-only indicator** that a tag is not
persisted to the repo. It is generated at display time, never stored, and never
used in queries.

- **Persisted tags** (user-applied or explicitly set) appear WITHOUT `%` prefix
- **Non-persisted tags** (auto-generated by the object's type or another entity)
  appear WITH `%` prefix in output only
- The `%` prefix is an indicator for the reader, not a query sigil — it means
  "this tag was computed/derived, not stored"
- Currently mostly unused but may appear in bats tests
- Do NOT confuse with the `%tag` query syntax, which is a completely separate
  concept (query for "objects tagged with `tag`")

### Object ID Disambiguation (Current)

Objects are disambiguated by their identifier structure:

- `!prefix` → type (has `!` sigil)
- `left/right` → zettel (has `/` separator between left and right parts)
- bare identifier → tag (no `!`, no `/`)

**Future**: True disambiguation will come from what genre (zettel, type, tag,
repo) the object's type expresses. In the complete absence of a type, the object
is ALWAYS a tag.

### Quoting

Values containing spaces are Go-quoted: `"like this"`.

### Date/Time

The MCP box format (`SkuFormatBoxTransactedNoColor`) excludes dates
(`BoxPrintTime = false`). The standard box format includes dates. The RFC should
specify both variants or make date inclusion configurable.

### Color

The MCP variant uses no color (`NoColor`). The standard box format supports
ANSI color output. The RFC should note that color is a presentation concern, not
part of the wire format.

### Description Placement

`BoxDescriptionInBox = false` means description appears OUTSIDE the brackets as
a trailer. When `BoxDescriptionInBox = true`, description appears inside
brackets (specify when this variant is used).

## Examples

```
# Zettel with type and tags
[thallium/golem !task area-home urgency-2_week] purchase izipizi glasses

# Zettel with blob digest
[ceroplastes/midtown @blake2b256-9ft3... !md project-2024-q3] meeting notes

# Type object (no description, has blob)
[!md @blake2b256-76m5... !toml-type-v1]

# Tag object (no type, no blob, with child tags)
[project-2021-zit area-career] store, organize, query, and edit files

# Tag object with a non-persisted (computed) tag shown in output
[project-dodder !toml-project-code %derived-tag] description here

# Minimal tag (no type, no tags, no description)
[zz-inbox]
```

## Query Sigils (Context for RFC)

These are NOT part of the box format itself but are relevant for understanding
how objects are addressed. Note: `%` has completely different meanings in query
context vs output context.

- `%tag` — **query sigil**: "objects tagged with `tag`" (NOT the tag object
  itself). This is unrelated to the `%` output prefix.
- `!type` — both the object-id prefix for types AND a query filter
- `:e` — genre filter for etiketten (tags)
- `:z` — genre filter for zettels
- `:t` — genre filter for types

The `%` prefix in box format output means "non-persisted/computed tag". The `%`
prefix in query syntax means "filter by tag". These are completely separate
semantics that happen to share the same character.

## Where to Find the Specification

### Code

- `go/internal/echo/box_format/` — box format implementation
- `SkuFormatBoxTransactedNoColor()` — the MCP variant (no time, no color,
  description outside brackets)
- `BoxTransacted` — the main formatter struct

### Bats Tests

The integration tests are the most complete specification of expected output.
Key files to examine:

- `zz-tests_bats/current_version/*.bats` — current version tests
- Look for tests using `-format box` flag
- Look for assertions matching box format output patterns
- `show.bats`, `query.bats`, `organize.bats` are likely starting points

### Trailing Whitespace

Trailing whitespace matters in dodder output assertions. Use `xxd` or `cat -A`
to debug invisible mismatches in bats tests.

## Open Questions for RFC

1. Should the RFC define a single box format or parameterized variants
   (with/without date, with/without color, description in/out)?
2. How should the `%` non-persisted tag output indicator be formally specified?
3. Should the RFC cover the query sigil syntax or keep it separate?
4. What is the canonical sort order for tags within brackets?
5. How should multi-line descriptions be handled (if at all)?
6. Should the RFC specify escaping rules beyond Go-quoting for spaces?
